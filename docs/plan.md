# Блок 0. Подготовка: где всё будет жить

Этот блок делается один раз, до написания кода. Его цель — чтобы к началу задачи A1 у вас был работающий путь «изменил файл → через минуту это видно в интернете».

## 0.1 Что мы вообще строим

Ваш генератор — это **статический сайт**. Слово важное, объясняю через аналогию.

Бывает два типа сайтов.

**Динамический.** Вроде интернет-магазина. Когда посетитель открывает страницу, где-то работает компьютер-сервер: лезет в базу данных, считает цены, собирает страницу и отдаёт. Такой сервер работает круглосуточно, стоит денег, ломается, требует обновлений безопасности. Вот для таких вещей и нужен Docker — он упаковывает сервер со всем его окружением, чтобы он одинаково работал везде.

**Статический.** Просто набор готовых файлов: HTML, CSS, картинки, JavaScript. Сервер ничего не считает — он отдаёт файлы как есть, ровно как файлообменник отдаёт вам скачиваемый архив.

Ваш генератор — второй тип. Вся математика — построение модели, экспорт STL и 3MF — считается **в браузере посетителя**, на его компьютере. Мы это специально так спроектировали.

Из этого следует:

- Сервера нет. **Docker не нужен, устанавливать его не надо.**
- Базы данных нет.
- Круглосуточно работающего компьютера нет.
- Хостинг статики бесплатен на любом разумном объёме трафика.
- Взламывать нечего: нет ни входа, ни базы, ни личных данных.

Если по ходу дела кто-то посоветует вам «поднять сервер», «настроить nginx» или «завернуть в контейнер» — для этого проекта это лишняя работа. Не потому что это плохие инструменты, а потому что у вас нет задачи, которую они решают.

## 0.2 Как это будет работать

Цепочка из трёх звеньев:

```
Ваш компьютер  →  GitHub  →  Netlify  →  посетитель
   пишете код     хранилище   сборка и     видит сайт
                    кода      публикация
```

**Ваш компьютер.** Здесь лежит папка с проектом, здесь вы (вместе с Claude) пишете код и смотрите результат локально.

**GitHub.** Это хранилище кода с историей изменений. Нужен по трём причинам: во-первых, там хранится каждая версия проекта, и можно откатиться к любой, если что-то сломали. Во-вторых, если ноутбук утонет, код цел. В-третьих — и это главное — хостинг умеет забирать код оттуда автоматически.

**Netlify.** Хостинг. Он следит за вашим репозиторием на GitHub. Как только вы туда что-то отправили, он сам скачивает код, собирает сайт и публикует. Вам не нужно ничего никуда «заливать по FTP» — это происходит само.

Слово «репозиторий» дальше означает просто «папка проекта на GitHub».

## 0.3 Что установить

Четыре вещи. Все бесплатные.

## Node.js

Это программа, которая умеет запускать JavaScript вне браузера. Нужна, чтобы собирать проект и запускать локальную версию сайта во время работы.

Скачать: **nodejs.org**, кнопка **LTS** (не «Current»). LTS означает стабильную версию, её и берите.

Проверить, что установилось — открыть Терминал (на Mac: Cmd+Пробел, набрать «Терминал»; на Windows: меню Пуск, «PowerShell») и ввести:

```
node --version
```

Должно ответить что-то вроде `v22.11.0`. Если ответило — готово. Если написало «command not found», перезапустите Терминал.

## Git

Программа, которая ведёт историю изменений и отправляет код на GitHub.

- **Mac:** ввести в Терминале `git --version`. Скорее всего уже установлен. Если нет — система сама предложит установить, соглашайтесь.
- **Windows:** скачать с **git-scm.com**, установить со всеми настройками по умолчанию.

После установки один раз представиться — Git подписывает каждое изменение вашим именем:

```
git config --global user.name "Ваше Имя"
git config --global user.email "ваша@почта.ru"
```

Почту указывайте ту же, на которую заведёте GitHub.

## Редактор кода

**VS Code** с **code.visualstudio.com**. Нужен, чтобы смотреть и править файлы. Даже если писать код будет Claude, вам понадобится видеть, что происходит.

## Claude Code

Он будет писать код прямо в папке проекта, читать ТЗ и `PROGRESS.md` сам и коммитить изменения. Устанавливается из приложения Claude на компьютере.

## 0.6 Проверить, что публикация работает

Прежде чем писать код, стоит убедиться, что вся цепочка живая. Для этого достаточно одной страницы.

Создать в корне папки файл `index.html` с содержимым:

```html
<h1>Скоро тут будет генератор</h1>
```

Отправить на GitHub:

```
git add .
git commit -m "Первая страница и документы"
git push
```

Три команды означают: «взять все изменения» → «записать их в историю с подписью» → «отправить на GitHub». Дальше это будет делать Claude Code, но полезно понимать, что происходит.

Теперь подключить хостинг. На **netlify.com**: **Add new site** → **Import an existing project** → **GitHub** → выбрать `gelstand-generator`.

Настройки сборки Netlify спросит сразу. Пока оставить пустыми:

- **Build command:** пусто
- **Publish directory:** пусто или точка

Нажать **Deploy**. Через полминуты Netlify даст адрес вида `random-name-12345.netlify.app`. Откройте — там должна быть ваша строчка.

**Это самая важная проверка во всём Блоке 0.** Если страница открылась, значит путь «файл на компьютере → интернет» работает, и дальше вы будете только менять содержимое, а не чинить инфраструктуру.

Имя сайта можно поменять: **Site configuration** → **Change site name**.

## 0.7 После задачи A1: поменять настройки сборки

В задаче A1 в проекте появится Vite. С этого момента сайт нужно **собирать** — превращать исходники в готовые файлы. Netlify сделает это сам, но ему надо сказать как.

В Netlify: **Site configuration** → **Build & deploy** → **Build settings**:

- **Build command:** `npm run build`
- **Publish directory:** `dist`

Сохранить. Дальше при каждом `git push` Netlify сам скачает код, соберёт и опубликует.

Тогда же добавить в корень проекта файл `.gitignore` со строкой:

```
node_modules
dist
```

Это список того, что не надо хранить на GitHub. `node_modules` — папка со сторонними библиотеками, весит сотни мегабайт и восстанавливается одной командой. `dist` — результат сборки, его делает Netlify. Если этот файл не создать, репозиторий распухнет и работать станет медленно. Claude Code создаст его сам, но проверьте, что он есть.

## 0.8 Домен

Бесплатный адрес `имя.netlify.app` работает полноценно, включая защищённое соединение. Для альфы этого достаточно.

Когда захотите свой адрес: купить домен у любого регистратора, в Netlify зайти в **Domain management** → **Add a domain** и следовать инструкции — там будет сказано, какие две строки прописать у регистратора. Сертификат безопасности Netlify выпустит сам и бесплатно.

Домен — единственная статья расходов в проекте, порядка 1000–2000 рублей в год.

## 0.9 Как выглядит рабочий день

После настройки цикл такой:

1. Открыть Терминал, перейти в папку проекта: `cd ~/Documents/gelstand-generator`
2. Запустить локальную версию: `npm run dev`. Она откроется на `localhost:5173` и будет обновляться при каждом сохранении файла.
3. Работать с Claude Code над задачей из плана.
4. Когда задача готова — отправить: `git add .`, `git commit -m "A2 — валидация"`, `git push`
5. Через минуту изменения на сайте.

Локальная версия и опубликованная живут отдельно. Пока вы не сделали `push`, в интернете остаётся предыдущая рабочая версия — сломать сайт случайным экспериментом нельзя.

## 0.10 Если что-то сломалось

**Сайт после публикации не работает, а локально работал.** В Netlify открыть вкладку **Deploys**, нажать на последнюю сборку, прочитать лог. Скопировать красные строки и показать Claude — почти всегда это опечатка или забытая зависимость.

**Нужно срочно вернуть как было.** В Netlify: **Deploys** → выбрать предыдущую удачную сборку → **Publish deploy**. Сайт мгновенно вернётся к ней. Это работает всегда и не требует ничего чинить.

**Сломали код у себя и хотите откатиться.** Каждый `commit` — точка сохранения. Попросите Claude Code вернуть к предыдущей, он знает как. Именно ради этого мы и делаем одну задачу — один коммит: точки сохранения получаются осмысленными.

## 0.12 Чего не делать

- **Не устанавливать Docker.** Он упаковывает серверное окружение, а у вас нет сервера.
- **Не арендовать VPS или виртуальный сервер.** Платить за круглосуточно работающий компьютер, чтобы он отдавал десяток файлов, незачем.
- **Не настраивать базу данных.** ТЗ прямо говорит: модели не хранятся, истории нет.
- **Не подключать CDN, кэши и системы мониторинга.** Netlify уже раздаёт файлы через свою сеть.
- **Не настраивать автоматические тесты в GitHub Actions.** Для альфы с одним разработчиком это обслуживание ради обслуживания.

Всё это — хорошие инструменты для задач, которых у вас нет. Каждый добавленный кусок инфраструктуры потом придётся чинить, обновлять и объяснять следующему человеку.

# Как вести работу при ограниченных лимитах

## Правило одной сессии

Одна задача — одна сессия — один коммит. Не начинать вторую задачу в той же сессии, даже если осталось место: недоделанный второй кусок придётся объяснять заново.

## Что положить в репозиторий до начала

```
/docs/tz.md          ТЗ v3 целиком
/PROGRESS.md         что сделано, что дальше, принятые по ходу решения
```

`PROGRESS.md` — самый ценный файл в проекте. Он заменяет память между сессиями:

```markdown
# Прогресс

## Сделано
- [x] A1 — каркас, состояние, константы
- [x] A2 — валидация + тесты

## Следующая задача
A3 — экспорт STL и 3MF

## Решения по ходу
- Плечи стойки оставлены константами 5,0 и 7,0
- Воркер не понадобился: худший случай 18 мс
```

## Шаблон начала сессии

```
Читай /docs/tz.md и /PROGRESS.md.
Делаем задачу <номер> из /docs/plan.md. Только её.
```

Три строки вместо пересказа проекта. Не прикладывать STEP-файлы заново — все числа уже в разделе 12 ТЗ.

## Чего не делать

- Не просить «заодно отрефакторить» — это удваивает сессию и ломает границу задачи.
- Не откладывать запись в `PROGRESS.md` на потом: если сессия оборвётся, следующая начнётся вслепую.
- Не делать задачу B1 в конце дня — она самая тяжёлая, ей нужен полный лимит.

# Блок A. Фундамент

Три задачи, полностью независимые от геометрии и интерфейса. Делаются первыми, потому что от них зависит всё остальное.

## A1. Каркас и модель состояния

**Вход:** ТЗ разделы 3, 5, 12.2
**Выход:** `src/state/`, `src/constants.js`, пустой `App`

1. `npm create vite@latest` → React. Удалить демо-контент.
2. `src/constants.js` — все константы из таблицы 12.2: `WALL = 1.5`, `BASE = 1.2`, `HEIGHT = 15.0`, `ARM_X = 5.0`, `ARM_Y = 7.0`, фаски, скругления.
3. `src/state/initial.js` — начальные значения раздела 3: ширина `'19,6'`, глубина `'37'`, `nx = 3`, `ny = 3`.
4. `src/state/reducer.js` — действия `setField`, `normalizeField`, `next`, `generateStart`, `generateOk`, `generateFail`, `reset`. Значения полей хранятся строками.
5. `src/state/snapshot.js` — `snapshot(state)` возвращает сериализованные нормализованные параметры.

**Готово когда:** приложение запускается, редьюсер покрыт парой ручных вызовов в консоли, значения полей — строки, а не числа.

---

## A2. Валидация

**Вход:** ТЗ разделы 5, 7, 16
**Выход:** `src/validation/`, тесты

1. `normalize(raw, kind)` — таблица 5.1: точка в запятую, округление до 2 знаков, подъём до 10, целое и минимум 1 для количества.
2. `validate(state)` — коды ERR-01 … ERR-07 и множество полей в состоянии `Error`.
3. Проверка габарита по формуле раздела 7: `nx × (ширина + 3) ≤ 500`, аналогично по Y.
4. `src/validation/messages.js` — словарь текстов ошибок отдельно от компонентов.
5. Тесты: `20.5 → 20,5`, `20,5678 → 20,57`, `5 → 10`, `0 → 10`, `nx = 0 → 1`, превышение по одной оси, превышение по обеим.

**Готово когда:** тесты проходят, включая случай одновременного превышения по X и Y (ERR-07).

---

## A3. Экспорт файлов

**Вход:** ТЗ раздел 15.2, готовый код из прототипа
**Выход:** `src/export/`

1. `exportSTL(mesh)` — бинарный STL.
2. `export3MF(mesh)` — zip без сжатия с `[Content_Types].xml`, `_rels/.rels`, `3D/3dmodel.model`, единица `millimeter`.
3. `fileName(params, ext)` — точка вместо запятой: `Nail_Modernism_Gelstand_19.6x37mm_3x3.3mf`.
4. Оставить один запускаемый скрипт-проверку: сгенерировать тестовый меш, записать оба файла, открыть 3MF штатным zip-ридером.

**Готово когда:** проверочный скрипт проходит, 3MF открывается в слайсере с правильным масштабом.

# Блок B. Геометрия

Самый рискованный блок. Делать на свежем лимите.

## B1. Профиль плитки и тайлинг

**Вход:** ТЗ раздел 12 целиком, `src/constants.js`
**Выход:** `src/geometry/build.js`

1. Подключить `manifold-3d`, инициализировать WASM.
2. Профиль основания плитки: прямоугольник `(w+3) × (d+3)` минус проём от `(5,0; 7,0)` до `(W−5,0; D−7,0)`.
3. Профиль стоек: в каждом углу плитки уголок из двух прямоугольников `5,0 × 1,5` и `1,5 × 7,0`.
4. Тайлинг: оба профиля размножить со сдвигом `(i × W, j × D)` и объединить в 2D.
5. Выдавливание: основание `0 … 1,2`, стойки `0 … 15,0`.
6. Вернуть `{ positions, indices, bbox }` по контракту 14.2.

Скругления и фаски **не делать в этой задаче.** Сначала правильные габариты и топология.

**Готово когда:** `build(19.6, 37, 3, 3)` даёт замкнутый манифолд с габаритом `67,8 × 120,0 × 15,0`. Это критерий 21 из раздела 20 ТЗ.

Если задача не помещается в сессию — разрезать по пункту 4: сначала одна плитка, потом тайлинг.

---

## B2. Скругления

# Порядок и зависимости

```
Блок 0 ── A1 ──┬── A2 ──┬────────────── D1 ── D3 ── D4 ── E1 ── E2 ── E3
               │        │                     │
               └── A3 ──┘               D2 ───┘
                                              │
B1 ── B2 ── B3 ───────────────────────────────┘

C1, C2, C3 — независимы, нужны к началу D1

Версия 4:

F1 ── F2 ── F3            смена движка, от остального не зависит
H1 ── H2 ──┬── H3
           └── H4
G1 ─────────── G2         G2 требует H2: без поля печати подбирать не от чего
```

Блоки F и H независимы друг от друга и могут идти параллельно. G1 тоже
независим, а вот G2 ждёт H2.

Блок C не зависит ни от чего и служит запасным вариантом: если на тяжёлую задачу лимита явно не хватит, лучше взять C1 или C3, чем начинать B1 и бросить на середине.

Задача B1 — единственная, где стоит держать запас: если после профиля плитки видно, что тайлинг уже не влезает, остановиться, записать состояние в `PROGRESS.md` и доделать в следующей сессии.
